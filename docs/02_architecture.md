# معماری و مدل داده

## چرا دو دیتابیس

داده در دو لایه نگهداری می‌شود تا هر لایه برای کار خودش بهینه باشد:

- workorders_source با مدل نرمال 3NF نگهدارنده داده پاک‌شده فایل خام است.
  شکل نرمال از افزونگی جلوگیری می‌کند و تغییر مراجع (شهر، دسته، وضعیت)
  را متمرکز می‌کند.
- workorders_dwh لایه تحلیلی است با اسکیمای ستاره‌ای: جدول Fact در مرکز و
  ابعاد دور آن. کوئری‌های تحلیلی به join های ساده تبدیل می‌شوند.

## مدل مبدا (3NF)

- region: یک ردیف برای هر شهر. region_code کلید طبیعی است و همان کد امور
  فایل است.
- work_category و order_status: مراجع دسته و وضعیت.
- open_work_order: جدول مشاهدات، با کلید خارجی به هر سه مرجع، در فرمت long.
  هر ردیف یعنی یک ترکیب شهر × ماه × دسته × وضعیت با تعدادش.
- قید UNIQUE روی (region_id, jalali_year, jalali_month, category_id,
  status_id) جلوی رکورد تکراری را می‌گیرد. سال و ماه SMALLINT هستند.
- ستون source_row شماره ردیف اکسل را نگه می‌دارد تا اگر عددی مشکل داشت
  سریع به ردیف اصلی برگردیم.

داده تجمیعی (ردیف‌های جمع فایل و ستون‌های «کل») در مبدا ذخیره نمی‌شود.
ذخیره داده مشتق نقض نرمال‌سازی است و در لایه تحلیل محاسبه می‌شود.

## مدل مقصد (ستاره‌ای)

- dim_date: کلید هوشمند YYYYMM مثل 140107، به همراه برچسب سال و نام ماه
- dim_city: city_id کلید جانشین و city_code کلید طبیعی
- dim_category و dim_status: با ستون order برای ترتیب پایدار نمایش
- fact_open_work_orders: سنجه open_count با قید UNIQUE روی ترکیب کلیدها
- etl_run_log: نتیجه هر اجرای ETL

چند نکته طراحی:

- سنجه fact مانده پایان ماه است و semi-additive. جمع روی شهر و دسته و وضعیت
  درست است ولی جمع روی زمان معنا ندارد.
- کلیدهای جانشین، fact را از تغییر کلیدهای طبیعی مستقل نگه می‌دارند و
  کلیدها را کوچک.
- کوئری‌های API همه star join هستند: fact به همراه چند dim.

## سرویس API

- ساختار: app factory با create_app و router ها در دو ماژول meta و analytics
- اتصال دیتابیس با تزریق وابستگی (Depends(get_conn)). برای هر درخواست یک
  اتصال از pool برداشته می‌شود و آخرش برمی‌گردد. pool_pre_ping اتصال مرده
  را بعد از ری‌استارت دیتابیس بازیافت می‌کند.
- تنظیمات با pydantic-settings از فایل .env خوانده می‌شود.
- همه کوئری‌ها SELECT هستند. API به دیتابیس تحلیلی فقط خواندن دسترسی دارد.
- خروجی endpoint ها با response_model های pydantic اعتبارسنجی و مستند
  می‌شوند. Swagger در /docs.

## Docker

- سرویس db: postgres:16 با volume پایدار و healthcheck با pg_isready
- سرویس api: ایمیج پروژه. depends_on با condition service_healthy باعث
  می‌شود استارت API تا آماده شدن دیتابیس عقب بیفتد.
- پورت‌های میزبان: 8080 برای API و 5433 برای دیتابیس. 5432 برای نمونه
  لوکال آزاد می‌ماند.
