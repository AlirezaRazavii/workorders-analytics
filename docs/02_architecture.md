# معماری و مدل داده

## دو دیتابیس و دلیل آن

داده در دو لایه نگهداری می‌شود تا هر لایه برای کار خودش بهینه باشد:

- workorders_source: مدل نرمال 3NF — نگهدارنده‌ی داده‌ی پاک‌سازی‌شده‌ی فایل خام.
  نگهداری داده در شکل نرمال از افزونگی جلوگیری می‌کند و به‌روزرسانی مراجع
  (شهر، دسته، وضعیت) را متمرکز می‌کند.
- workorders_dwh: اسکیمای ستاره‌ای — لایه‌ی تحلیلی. جدول Fact در مرکز و
  ابعاد دور آن؛ کوئری‌های تحلیلی به join های ساده و مستقیم تبدیل می‌شوند.

## مدل مبدا (3NF)

- region: یک ردیف به ازای هر شهر، region_code کلید طبیعی (کد امور فایل)
- work_category و order_status: مراجع دسته و وضعیت
- open_work_order: جدول مشاهدات با کلید خارجی به هر سه مرجع، در فرمت long
  (هر ردیف = شهر × ماه × دسته × وضعیت × تعداد)
- قید UNIQUE روی ترکیب (region_id, سال, ماه, category_id, status_id) تکراری
  نبودن مشاهدات را تضمین می‌کند.
- ستون source_row شماره ردیف اکسل را نگه می‌دارد برای ردیابی خطا (lineage).

داده‌ی تجمیعی (ردیف‌های جمع فایل و ستون‌های «کل») در مبدا ذخیره نمی‌شود؛
ذخیره‌ی داده‌ی مشتق نقض نرمال‌سازی است و در لایه‌ی تحلیل محاسبه می‌شود.

## مدل مقصد (ستاره‌ای)

- dim_date: کلید هوشمند YYYYMM (مثلا 140107)، به‌علاوه برچسب سال و نام ماه
- dim_city: city_id کلید جانشین (surrogate)، city_code کلید طبیعی
- dim_category و dim_status: مرتب‌سازی با ستون order برای نمایش پایدار
- fact_open_work_orders: سنجه‌ی open_count با قید UNIQUE روی ترکیب کلیدها
- etl_run_log: نتیجه‌ی هر اجرای ETL

نکته‌های طراحی:

- سنجه‌ی fact نمایش مانده‌ی پایان ماه است (semi-additive). جمع روی شهر، دسته
  و وضعیت معتبر است؛ جمع روی زمان معنا ندارد و روند باید مقایسه‌ای تحلیل شود.
- کلیدهای جانشین در ابعاد، جدول fact را از تغییر کلیدهای طبیعی مستقل می‌کنند
  و اندازه‌ی کلیدها را کوچک نگه می‌دارند.
- کوئری‌های API همه به شکل star join هستند: fact + چند dim.

## سرویس API

- ساختار: app factory (create_app)، router ها در دو ماژول meta و analytics
- اتصال دیتابیس با تزریق وابستگی (Depends(get_conn)): به ازای هر درخواست یک
  اتصال از pool برداشته و پس از پایان برگردانده می‌شود. pool_pre_ping اتصال
  مرده را بعد از ری‌استارت دیتابیس بازیافت می‌کند.
- تنظیمات با pydantic-settings از فایل .env خوانده می‌شود.
- همه‌ی کوئری‌ها SELECT هستند؛ API به دیتابیس تحلیلی فقط خواندن می‌کند.
- خروجی‌ها با response_model های pydantic اعتبارسنجی و مستند می‌شوند
  (Swagger در /docs).

## Docker

- سرویس db: postgres:16 با volume پایدار و healthcheck (pg_isready)
- سرویس api: ایمیج پروژه؛ depends_on با condition service_healthy باعث می‌شود
  استارت API تا آماده شدن دیتابیس عقب بیفتد
- پورت‌های میزبان: 8080 برای API و 5433 برای دیتابیس (5432 برای نمونه‌ی لوکال
  آزاد می‌ماند)
